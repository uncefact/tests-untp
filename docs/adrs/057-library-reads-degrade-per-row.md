# ADR-057: Library reads return every readable record and name the ones they cannot

- **Date:** 2026-09-09
- **Status:** accepted

## Context

The library list (`GET /api/v1/library`, #962), the bulk fetch (`POST /api/v1/library/batch-get`, #963) and the detail route (`GET /api/v1/library/{id}`) all read records through one strict pipeline: the repository narrows each row to its origin (`narrowLibraryRecord`, `hydrateLibraryRecords`) and the projector turns it into the published `CredentialRecord` shape (`toCredentialRecord`, `toNativeCredentialRecord`, `toCredentialRecordDetail`). Every step throws when a row breaks an invariant of the read model (ADR-053): an external record with no check run, a native record with a generation 1 run, a settled run with no completion timestamp, a failed run with no failure recorded. The detail route adds one more step, revealing the stored key, which fails for a malformed envelope, missing key configuration or a failed unwrap. Until now a throw anywhere in that pipeline failed the whole request with a sanitised 500 that named neither the record nor the cause, and the batch route silently omitted ids that were missing, belonged to another tenant, or carried a NUL byte.

This decision was forced by the review of #963. An integrator who issued a credential and then asked for it by id could get a 500 for the whole batch because a neighbouring row was damaged, with no way to tell which id or why. #769 had recorded the same question for the old credentials list, where one row whose key could not be revealed failed the page; that route is retired by #965 (ADR-052), but the library routes had inherited the behaviour. The client contract had deferred a per-id status on batch-get ("considered and deferred; not built for v1"); the owner reopened that deferral, and this record settles it before v0.5 is cut.

The database does not make these rows impossible. Composite foreign keys and deferred triggers keep a parent and its child together (ADR-053), but `CheckRun`'s completion and failure columns are nullable with no state-conditional constraint, so a run that says `FAILED` with no failure recorded is storable, and a projector rule can tighten after rows were written. A row that cannot be read is therefore a real, if rare, state of a healthy deployment, not only a sign of a bug.

## Decision

1. **A collection read returns every readable record and lists, by id, each one it could not read. It never fails the whole response for a bad row.** `GET /api/v1/library` and `POST /api/v1/library/batch-get` answer 200 with `data` (the readable records, unchanged in shape) and a required sibling `failures` array of `{ id, code, message }`, which is empty when every record was readable. When every record failed, `data` is empty and `failures` carries one entry per selected or requested id; the response is still 200. Nineteen readable records are not lost to one damaged neighbour, and the caller learns exactly which id to raise. A database or transaction failure, and a selection-level invariant failure, are still whole-request errors under ADR-036, because no per-id outcome can be truthfully fabricated when the read itself did not complete. Authentication, tenant assignment and request validation answer as they do today; only the outcomes of a valid, authenticated read are collection outcomes.

2. **A batch read accounts for every distinct id it was given.** The distinct submitted ids equal the ids in `data` plus the ids in `failures`, with no overlap and first-appearance order kept within each array. An id that is missing, belongs to another tenant, or carries a NUL byte is reported as `NOT_FOUND` with one code and one message, so the response cannot be used to probe another tenant's ids; a NUL-bearing id still never reaches SQL. This replaces the silent omission the client contract had deferred to, so a caller no longer diffs the response against its request to notice an absence.

3. **Two public codes describe a collection failure, in the caller's terms.** `RECORD_UNREADABLE` means the record is the caller's and exists but could not be read. Stored state this API cannot represent is the usual cause, and the code also covers any other fault local to that one record, because a caller acts on both the same way and a service defect must not be published to them as damage to their data. The message says the record exists and belongs to their tenant, which is what tells them to raise it with an operator rather than re-check their own id, and asks them to quote the id and the `x-correlation-id` response header. `NOT_FOUND` is the existing code reused. No code distinguishes a missing child from an illegal verification envelope, because that distinction changes the operator's repair and not the caller's action. No message advises re-verifying or deleting: re-verification needs the same read, and deleting is not advice this service should give about a record the caller cannot inspect. Deletion is available for an external record since #1032, but it is not a route out of this state either. The delete path reads the record through the repository's shared record read before removing it, and that read narrows the row and then asserts its check-run invariant, so an external record whose stored shape is broken, one with no check run for example, answers a sanitised 500 on `DELETE` as well and cannot be removed through the API; a record that passes that read and fails only in projection can be. The message therefore advises neither deletion nor re-verification and points the caller at an operator, which is the one step that helps in both cases.

4. **The detail route returns the record it has built even when it cannot return the key.** `GET /api/v1/library/{id}` answers 200 with the record, `hasKey: true`, `decryptionKey: null` and a `warnings` entry with code `DECRYPTION_KEY_UNAVAILABLE` when the stored key envelope is malformed, the deployment's key configuration is missing, or the unwrap fails. The record is built before the key is touched, so discarding it to report the key would repeat, one level down, the whole-response failure decision 1 removes. The detail schema's custody rule becomes a closed set: a non-null key requires `hasKey: true` and a non-null `storageUri`; `hasKey: true` always requires a non-null `storageUri`, so a held key with no copy location stays an unreadable record rather than a key warning; `hasKey: true` with a null key requires exactly one `DECRYPTION_KEY_UNAVAILABLE` warning; `hasKey: false`, and a non-null key, forbid it. A null key therefore stays unambiguous, and the custody claim (ADR-055 decision 5) is never falsified by a fabricated `hasKey: false`. The warning code belongs to the detail response only: list and batch rows carry no key and their schema forbids it. A record that cannot be built at all answers `500 { error, code: 'RECORD_UNREADABLE', id }`, where `id` is always the requested id; a request-level fault (a database or transaction error, ADR-036) keeps the shared sanitised 500; `404 NOT_FOUND` is unchanged. The route's two stages reach that split by opposite rules, and deliberately. The read stage is classified POSITIVELY, so only a recognised record-shape failure becomes the coded body and anything else it raises takes the sanitised one, because the read is where a request-level fault originates and `isDatabaseError` is not guaranteed to recognise every one of them. Building the record is pure computation over a view the route already holds, so that stage is classified by exclusion and any throw from it is this record's failure, which is the rule the collection routes apply to a row.

5. **Only a failure that can be attributed to a caller's id becomes a per-id outcome, and the id is checked against the selection before it is published.** A hydration result that returns a row that was never selected, a duplicate row for one id, or a cardinality mismatch with no nameable missing id breaches the selection boundary and stays a whole-request sanitised 500. No request an authenticated tenant can send reaches that state: the repository's own guards run first, so this check is defence in depth against a defect in that layer, and it is worth its cost because it sits at the last code that touches an id before a response body is written and because the identity it would otherwise publish cannot be recalled. Every failure entry's id is the id of the parent being processed (the URL id, the selected page id, or the submitted id), never an id read off the error. Some projection errors name the run's record rather than the parent, so the classifier compares the error's id for equality with the parent, not for membership in the selection, because with two selected ids an error naming the second while processing the first would otherwise be filed as an ordinary projection failure. That comparison's product is the operator's diagnosis and nothing else: keeping a foreign id unpublished is structural, since both paths build the published failure from the parent id before the error is examined at all. On a mismatch the parent is reported `RECORD_UNREADABLE`, the foreign id is never published, and the log carries both ids. The parent is the caller's own selection and the tenant boundary was already enforced by the hydration queries, so the disagreement is a row-local fault and does not cost the page. Any other throw local to one row's narrowing or projection becomes that row's `RECORD_UNREADABLE`, so a page is never aborted by a row-local fault. Classification is by failure kind and trusted identity carried on the error, never by matching message text.

6. **Pagination counts the page as selected, not as read.** `pagination.total` counts matching records including unreadable ones, and `hasMore` is computed from the consumed page (`data.length + failures.length`), so a final page with a failed row does not claim more records remain and an all-failed page that is not the last still says more remain. Clients advance by `limit`, never by the number of records received; a client advancing by `data.length` would re-request an all-failed page forever. Failed rows are never backfilled with extra records, because that would make the page consume a different selection from the one requested.

7. **The correlation id reaches the caller by the existing `x-correlation-id` response header, not by a body field.** The middleware already sets that header on every `/api/v1` response, so a body field would duplicate it on two routes and omit it everywhere else.

8. **Every degraded record is logged once, with what the operator needs and nothing the caller must not see, because a 200 hides the degradation from HTTP-error monitoring.** One error-level event per degraded record, including the detail route's key-unavailable outcome, carries the record id, correlation id, tenant, route, read stage, public code, internal reason and a safe detail, never a stored envelope, key or raw record; the route's classifier owns that event, so the key-reveal helper is told by that caller not to log its own error line, which avoids a second error per failure on this route while the helper's other callers keep their signal; one summary line per request carries the returned, unreadable and not-found counts. The operational documentation names this event as the signal to watch, since the failure no longer appears as a 5xx.

9. **Outcomes keep selection order.** The route walks the original selection once, so a hydration failure on a later id and a projection failure on an earlier one keep their positions in `failures`, and a batch keeps first-appearance order within each array.

## Consequences

Easier: a damaged row is visible by id in the response and in the log, and the rest of the library keeps working; an integrator's batch loop has one code path for the healthy, mixed and all-failed cases; the detail route always yields the verification result even when the key is out of reach, so a poller no longer needs a separate keyless read.

Harder: clients of the unreleased v0.5 contract must consume `failures` on a 200, advance pagination by `limit` rather than by rows received, handle an explicit `NOT_FOUND` per id, and read the detail warning; the client contract is amended before v0.5 ships. Corruption no longer surfaces as a 5xx rate; the per-record log event is the signal, and wiring an alert to it is an operator obligation recorded in the operational documentation, not something this change installs. Because that documentation asks deployments to alert on the event's `reason` and `code` values, those values are an operator-facing compatibility surface from this decision onward: they are renamed with the same sweep an API code gets, and a test holds the emitted `reason` set equal to the documented one.

## Alternatives considered

- **Keep failing the whole response.** Rejected. One damaged row hides a tenant's entire library, and the sanitised body names neither the id nor the cause, so the caller cannot even report it.
- **Degraded entries inside `data`.** Rejected. Every consumer parses each `data` entry as a strict `CredentialRecord`; a client mapping rows to a table crashes on the entry with no `credential` while its neighbour is valid.
- **An envelope around every entry.** Rejected. A wholly healthy page changes every field access for the rare failure, and it changes the list contract already shipped in #1022.
- **A 207 status, or an error only when all rows fail.** Rejected. 207 carries WebDAV semantics and no automatic meaning for this JSON; flipping the status when the last healthy row breaks gives a caller two code paths for one outcome.
- **Continue omitting missing ids from batch-get.** Rejected. A request for one missing id returned nothing to act on, and the accounting rule in decision 2 cannot hold with omission.
- **Distinguish a foreign id from a missing one.** Rejected. A guessed id would reveal that another tenant holds a record.
- **A detail 500 when only the key is unavailable.** Rejected. The route has already built the record; discarding it repeats the whole-batch mistake one level down, and forces a poller onto a second route to read a verification result it could have had.
- **A `correlationId` body field.** Rejected. It duplicates the existing response header on two routes only.
- **Filter or backfill parameters.** Rejected. A caller cannot ask about a failure it does not know exists, and backfilling changes which records a page consumed.
