# ADR-043: Data-backfill conventions

- **Date:** 2026-08-16
- **Status:** accepted

## Context

The reference implementation now has two data backfills, wired in opposite ways, and a third author has no rule to follow. This ADR records the rule so the next backfill does not have to rediscover it from a code review.

A data backfill rewrites existing rows so they match what the current application expects, rather than changing the shape of the tables. [ADR-024](./024-database-migration-discipline.md) covers schema migrations and the expand/contract pattern, and it names the backfill as a step that happens "often a separate step, possibly out-of-band" without saying how that step is wired. This ADR fills that gap.

Rewrites also happen inside migration SQL, where an `UPDATE` exists to make the migration's own DDL valid (`20260303000000_add_render_method_type` fills a column before `SET NOT NULL`, and `20260528000000_align_cvc_for_ingest` remaps enum values so the old type can be dropped). This ADR does not govern those. It covers standalone backfill scripts, which are the ones that need application code and run after `prisma migrate deploy`. DML inside `prisma/migrations/**/migration.sql` stays with ADR-024, because when a migration may collapse expand and contract into one file is that ADR's question.

The two existing backfills are:

- **Hex to multibase digests** (`packages/reference-implementation/prisma/backfills/2026-05-19-hex-to-multibase.ts`). It pairs with the migration that renamed `hash` to `digestMultibase` and transcodes the legacy hex values the rename left in place. It runs automatically on every container start, from `docker-entrypoint.sh`, after `prisma migrate deploy`. A value it cannot parse as either shape is left alone and warned about, and a value it does convert keeps the same digest bytes in a different encoding, recoverable from the stored value alone with `MultibaseDigest.fromString`. So a run against a database it was not meant for rewrites representations it can always turn back, without reaching for the credential content or any secret.
- **Decryption-key encryption at rest** (`packages/reference-implementation/scripts/backfill-decryption-keys.ts`, from #697). It wraps plaintext credential decryption keys in encrypted envelopes under `DATA_ENCRYPTION_KEY`. It ships in the image but runs only when an operator invokes it. Before writing anything it decrypts every existing envelope to prove the configured key is the right one, and when no envelope exists to prove it against, it refuses to write unless `--force` is passed. Its worst case under wrong input is unrecoverable: keys wrapped under a key nobody holds cannot be unwrapped, and the credentials they open become unreadable.

The difference between them is deliberate. The deciding property is whether a run against the wrong input can be undone, rather than anything about size, duration, or how recently the backfill was written.

## Decision

**1. A backfill may run automatically at startup only when a run against the wrong input can be undone from the data it leaves behind. Where it cannot, the backfill is operator-run.** The question to ask of a candidate is what a run against a database or an environment it was not meant for leaves you holding. Transcoding a digest leaves the same bytes in a different encoding, which anyone can turn back without a secret, so nobody gains from a human typing the command. Wrapping a key under the wrong `DATA_ENCRYPTION_KEY` leaves a value nobody can unwrap, so a human chooses the moment, having taken a backup and checked the environment. The undoable case is not the same as an untouched database: the digest backfill does rewrite the rows it recognises, and calling that "no change" would mislead the next author into auto-running something whose writes are merely reversible in theory.

**2. Being undoable admits a backfill to the startup path. It does not qualify it.** Point 1 is necessary and not sufficient, because the startup path also decides whether the instance boots at all. An auto-run backfill must additionally hold no external side effects (the digest backfill never re-fetches storage and never touches `storageUri` or `storageUrl`, which is what keeps a wrong-database run local to the row), take no long transaction or table lock, and read in pages rather than loading a table into memory. The reason is the entrypoint: it runs under `set -e`, so a backfill that throws stops the container from starting, and the rows it already wrote stay written. A backfill that is harmless per row and scans a large table unpaginated still takes the instance down, and `SKIP_BACKFILLS` only lets it boot with the old values in place, which is an escape hatch rather than a fix. The existing digest backfill predates this rule and does load both tables with a single `findMany`. New auto-run backfills paginate, as the operator-run path already does.

**3. Auto-run backfills live in `packages/reference-implementation/prisma/backfills/`, are named for the date they were introduced followed by a slug (`2026-05-19-hex-to-multibase.ts`), and go live only when a line invoking them is added to `docker-entrypoint.sh` after `prisma migrate deploy`.** They sit beside the migrations they pair with because they are part of the same upgrade step, and the date prefix records when each was introduced. The entrypoint holds an explicit ordered list rather than scanning the directory, so a correctly named file that nobody wires up never runs, and the list, not the filename, is what decides execution order. Running after `migrate deploy` means the columns they write have already been renamed or added. Two constraints come with that wiring. The first is that the backfill block sits inside the `SKIP_MIGRATIONS` guard, so `SKIP_MIGRATIONS=true` skips every auto-run backfill as well, and a deployment applying migrations out of band must run the backfills out of band too. To skip the backfills alone, set `SKIP_BACKFILLS=true`. The second is that a retained script runs after every later migration, so it is removed in the same change that drops or renames a column it reads, never before, because otherwise every boot after that migration fails.

**4. Operator-run backfills live in `packages/reference-implementation/scripts/`, alongside the other maintenance commands, with a `pnpm` script alias in the package manifest.** They are not startup wiring, so they do not belong under `prisma/`. The alias (`pnpm backfill:decryption-keys`) is the source-checkout entry point.

**5. Both kinds ship inside the published Docker image and are invoked there through `node_modules/.bin/tsx`.** The image has no package-manifest entry point, because the runtime stage copies no `packages/reference-implementation/package.json` into `/app`, so the `pnpm` alias has no script to resolve and the `tsx` path is the in-image interface. An operator-run backfill offered only as an alias would be unrunnable exactly where it is most often needed, on a released image with no source checkout. Shipping is not automatic beyond the two directories: `prisma/backfills/` and `scripts/` are copied wholesale, while the `src/lib/` modules those files import are copied file by file, so a new script that imports a module outside that list works in a checkout and fails in the image until a matching `COPY` is added to the runtime stage. Each operator-run script's header states both invocations, the checkout one and the `docker compose exec` one.

**6. Every backfill is idempotent, converges rather than erroring on a second run, and never writes a conversion over a value that changed after it was classified.** Auto-run backfills execute on every container start, so a non-idempotent one would corrupt data on the second boot, and operator-run backfills are re-run after a rolling upgrade drains old writers, so the second run must be a no-op over the rows the first one handled. Idempotency here means recognising an already-converted value and leaving it alone, not tracking which rows have been visited. The second half of the rule covers the live writer: a backfill that reads a snapshot and then updates by id alone can overwrite a value the application wrote in between, which during a rolling upgrade is a serving replica's write being replaced by a conversion of the stale one. So the write is conditional on the value the row still holds, by a `WHERE` on the classified value or a re-read. A run that fails part way leaves its committed rows converted, and the retry must converge over them.

**7. A backfill whose run cannot be undone proves its dangerous input read-only before its first write, and refuses to write when it cannot.** Because the result cannot be undone, an after-the-fact check is worthless: by the time the operator sees a decryption error, the plaintext is gone. So the preflight decrypts every existing envelope and aborts on any failure, which turns a wrong-key run into a clean refusal, and `--force` does not bypass that abort. Where no envelope exists to prove the key against, the safe default is to refuse rather than to guess, and `--force` is the operator's explicit acceptance of that one unverifiable case, with a warning that names the consequence. The proof is point-in-time: it holds for the rows that existed when it ran, so it stands in for stopping writers rather than replacing it.

**8. An operator-run backfill leaves the old shape readable, rather than assuming the conversion has happened.** Nothing forces an operator to run one, so the application must keep serving an instance that never did. This is what makes the human gate safe rather than merely cautious, and it is why the key backfill can sit unrun indefinitely: the read path still accepts a plaintext key. A conversion the application cannot read until someone runs a command is an outage waiting on a person.

**9. A read-only preview belongs in a sibling audit command, not as a `--dry-run` flag on the backfill, when the preview answers a question operators ask outside the backfill's window.** The encryption audit (`pnpm audit:encryption`, #764) exists because "does the active key decrypt everything stored?" is asked before a key rotation, after a backup restore, and during incident triage, none of which involve running the backfill. A flag would bury that capability behind a command an operator has no other reason to run, and would tie a durable capability to a script whose life is shorter than the question it answers. Where a preview genuinely only makes sense as "what would this specific backfill do", a flag on the backfill is the right home.

**10. Each backfill gets a reference page under the operations documentation's Backfills section. The Startup page summarises the auto-run ones, and migration guides carry the upgrade journey and link to the reference pages.** The three surfaces answer different questions. The reference page answers "what does this backfill do and how do I run it" for as long as the backfill exists. The Startup page answers "what happens when my container boots", which is where an operator looks when a boot does something they did not expect. The migration guide answers "what do I do to get from version N to N+1", and it is frozen at its release, so durable command reference kept there goes stale where the reference page does not. This ADR fixes where the pages belong, and the tree does not match it yet. Building the Backfills section and slimming both migration guides is #772, and documenting the backfills step on the Startup page is #767.

## Consequences

The wiring question is answered before it is asked, and it is answered by a property of the backfill rather than by whoever reviews the PR. A reviewer can check a new backfill against points 1 and 2 in a sentence.

Auto-run backfills accumulate in the startup path. Each one scans its table on every boot, so a large instance pays that scan forever. Point 3 fixes only the one lifetime question the entrypoint forces, namely that a script goes when the column it reads goes. When a backfill may be removed simply because every deployment has converted stays open, and so do the questions underneath it: how completion is recorded or inferred, what happens to a restored old backup or a dormant instance that skipped the upgrade, and what upgrade window is supported. Deleting a script too early leaves such a database permanently wrong, so until that decision is made, scripts stay.

Operator-run backfills can be missed. Nothing forces an operator to run one, so an instance can sit indefinitely with rows the application still handles but no longer writes, and nothing in the boot path reports that. Point 8 is what makes this survivable rather than a defect.

The existing digest backfill does not meet point 2's pagination constraint, and no test covers it. Both are pre-existing and neither is fixed here.

The preflight in point 6 costs a full pass over the encrypted stores before any write, which grows with the data. It is bounded by the same work the audit command already does, and it runs once per invocation rather than per row.

## Alternatives Considered

**Run every backfill automatically at startup, keeping the preflight.** Rejected, and this is the strongest form of the alternative rather than the naive one: the preflight from point 7 already prevents a silent wrong-key run, aborting before any write and refusing when it cannot prove the key. Two things it cannot do defeat the automatic form. A correct wrap is still a one-way door for the deployment, because an earlier application version rolled back onto a converted database returns raw envelope JSON, and the moment to accept that is a deploy decision no preflight can take. And point 6 needs old writers drained before the run, which a replica booting mid-upgrade cannot wait for. A backup before a one-way door is a human's call.

**Run every backfill on operator invocation.** Rejected. The undoable ones then depend on an operator noticing a release note, and an instance that misses one holds values the current writers no longer produce, with nothing in the boot path to report it. For a backfill whose writes can be turned back, the human gate adds a failure mode and buys nothing. A stronger variant, refusing to boot until an undoable backfill has converged, was also rejected: it converts a silent inconsistency into a hard outage over values the application still reads.

**Decide by size or duration instead.** Rejected as the primary key, though duration is not irrelevant. A long backfill on a large table is an availability concern, which is why point 2 makes pagination and lock-freedom admission constraints in their own right. It does not become safer for a human having typed the command, while a short one that wraps keys under an unproven key is catastrophic in seconds. Duration predicts how long a boot takes, not whether a mistake can be undone.

**Keep both kinds in one directory.** Rejected. The directory is the first thing an author sees and the cheapest place to carry the distinction. Splitting `prisma/backfills/` from `scripts/` also matches what the two are: one is part of the startup sequence that lives beside the migrations it pairs with, the other is a maintenance command that sits with the other maintenance commands.

**Give the destructive backfill a `--dry-run` flag instead of a sibling audit command.** Rejected for this case. The preview is asked for at moments that have nothing to do with running the backfill (before a key rotation, after a restore, during triage), and the question outlives the one-off script. A flag would tie a durable capability to a disposable one. This rejection is scoped: where a preview is genuinely only meaningful as "what would this one backfill do", the flag is correct, which is why point 9 states the test rather than banning the flag.

**Ship operator-run backfills only as a pnpm alias.** Rejected. The runtime image carries no package manifest for the reference implementation, so there is no script for the alias to resolve, and the operators most likely to need a backfill are on that image rather than a source checkout. An alias-only command is unrunnable exactly where it is needed.

**Decide here when a rewrite may live in migration SQL instead.** Rejected as out of place. Inline DML exists to make a migration's own DDL valid, so ruling on it is ruling on when a migration may collapse expand and contract into one file, which is ADR-024's question and needs its own design fork. Neither exemplar here could have been inline SQL, because both need application code. Scoping this ADR to standalone scripts and saying so is honest. Adding a "prefer inline when it is small" line would decide a third mechanism from evidence this ADR does not hold.
