# ADR-062: Outbound request retry lives in the HTTP client

- **Date:** 2026-10-21
- **Status:** accepted

## Context

Every outbound call the services package makes goes through `httpFetch` in `packages/services/src/http/client.ts`, which made a single attempt. When a dependency, or a gateway in front of it, answered `429` or `503` for a moment, the call failed although the same request a few seconds later would have succeeded. The operator backfills reported such a refused status read as `unavailable` evidence, so a run making many reads in quick succession could report many of them. The batch issuance job retries whole items (ADR-060), but nothing retried a single request (#1117).

Whether a request may be sent twice depends on what it does, not on its HTTP method. VCKit's verification and status reads are `POST` requests that change nothing. A credential issue, a document store or a link registration may already have taken effect when the response is lost or refused, so sending it again after a `503` or a timeout can add a second effect.

Status-list mints and status changes run inside a transaction-scoped advisory lock with a deadline (ADR-058 decisions 6 and 7). A batch item already has its own retry ladder for the faults before its credential request is dispatched, so a request retry there would multiply attempts against a dependency that is already refusing. Nothing issues the item again after a fault from dispatch on.

## Decision

1. **Retry lives in `httpFetch`.** Every adapter call and every call the Reference Implementation makes through it can retry. The policy is pure functions in `retry-policy.ts` beside the client. The client and its retry scope are exported from the services `./server` entry, so the Reference Implementation's own stored-copy readers use the same code.

2. **A `429` is retried for every call.** This rests on an assumption about the deployment's gateways: that a `429` from a dependency, or from a gateway in front of it, means the request was refused before it was acted on. RFC 6585 defines `429` as rate limiting and does not say whether the request was processed, so nothing in the status code guarantees it. The effects of a resend when a gateway breaks that assumption are listed on the [Outbound request retries](../../documentation/docs/reference-implementation/operations/outbound-retries.md) page.

3. **A `503`, and an attempt that receives no response headers within its time limit, are retried only for a call its adapter marks repeatable.** The marking is per call site. The repeatable calls are VCKit verification and status reads, VCKit DID resolution and key lookup, identity resolver link, description and vocabulary reads, and reads of the deployment's own stored copies. A repeatable call may also set a per-attempt limit. DID key lookup (`didManagerGet`), the identity resolver reads and stored-copy reads set 10 seconds. Verification, VCKit status reads (`checkBitstringStatus`) and DID resolution (`resolveDid`) set none, because VCKit fetches remote JSON-LD contexts while it verifies, fetches the status list credential from its URL while it answers a status read, and resolves remote `did:web` documents, and none of these calls had a limit before. An attempt with no limit of its own is bounded by the caller's signal only where the caller supplies one. DID resolution (`resolveDid`, reached through `getDocument` from DID creation, the DID document route and the seed) and the public verification route (`POST /api/v1/credentials/verify`) supply neither a signal nor a per-attempt limit, so this client does not bound an attempt they have sent, apart from reading a refused response's body before a wait, which stops at the 30 second default deadline (decision 5). A connection failure, a `502`, a `504` and every other status are not retried for any call.

4. **Backoff is exponential with full jitter.** A call makes at most four attempts. The wait before resend `n` is a uniform draw up to `min(5 s, 500 ms × 2^(n−1))`. While attempts are capped at four the steps are 0.5, 1 and 2 seconds, so the 5 second cap is not reached. A `Retry-After` header on a retried `429` or `503` is a floor the wait never goes below. The header is read as delay-seconds or as any of the three HTTP-date forms RFC 9110 requires a recipient to accept. A value that is neither, or one longer than 30 seconds, ends the retry and returns the response. An unreadable value ends the retry because it cannot be honoured, and the client never resends sooner than the server asked. The HTTP-date grammar is `parseHttpDate` in `retry-policy.ts`, because `parseImfDate` in `@uncefact/untp-utils/http-headers` returns the header string rather than an instant and accepts IMF-fixdate only. Moving the parser into `untp-utils` beside it is a follow-up.

5. **Retrying never outlives the caller.** A call's deadline is the caller's own when one is passed, otherwise 30 seconds from the first attempt (`DEFAULT_RETRY_BUDGET_MS`), and each wait is capped at the smaller of 30 seconds and the time left. The VCKit adapter passes `GetCredentialStatusInput.deadline` as a status read's deadline and `VerifyOptions.deadline` as a verification's. The deadline bounds waits and the dispatch of retries. No retry is dispatched and no wait ends after it. An attempt already sent is bounded by its per-attempt limit, where it has one, and by the caller's signal, where one is supplied, not by the deadline. The exception is the read of a refused response's body before a wait, which also stops at the deadline (decision 6). After a wait the client checks the caller's signal and the deadline immediately before it dispatches the next attempt. A signal that fires during a wait returns the preceding response, whose body the client has already read in full, or throws the preceding attempt's error when that attempt timed out. A signal that fires during an attempt throws that attempt's error. A per-attempt limit, when a repeatable call sets one, runs only until the response headers arrive.

6. **After retrying ends, the caller sees what one attempt with the final outcome would show.** The last response is returned, or the last error is thrown, so every adapter's existing error mapping applies. That response's body is unread unless the client read it before a wait, in which case the caller gets the copy described below, without `content-encoding` and `content-length`, or a body that fails to read if that read did not finish. Before each wait the client reads the refused response's body in full, while the caller's signal still applies and no later than the deadline. It holds a copy built from those bytes across the wait, with the same status, status text and headers, less `content-encoding` and `content-length` because the bytes are already decoded. When the refusal held across a wait is itself returned, because the caller's signal or the deadline ended the retry during or after that wait, the caller gets that copy, so its body reads in full without the network. A response from a later attempt is returned as received. If the read fails, the client neither waits nor retries. It returns a response with the same status and status text, and the same headers less `content-encoding` and `content-length`, whose body rejects with the error that ended the read: the caller's abort reason or the network error. If the deadline arrives during the read, the client cancels the read, which closes the connection, and gives up. It returns a response with the same status, status text and reduced headers whose body rejects with a `TimeoutError`. The client reads the original body through its own reader, not a clone, and that is what leaves nothing a later abort could reject unhandled: a clone leaves an unread branch that rejects with no handler when the caller's signal aborts later, and Node then ends the process. However the read ends, the client then removes its listener from the caller's signal, because the copy needs no network. A response returned before the client has read its body keeps its one listener, so the caller's signal can still end that read. A stream request body gets one attempt, because it cannot be sent twice.

7. **Calls made under the status-list lock never wait.** The VCKit adapter's status mint and status set make one attempt (`retry: false`), so a refusal cannot hold the lock for the length of a backoff. This narrows decision 2 for those calls. Status reads before and after a change run outside the lock and are retried as reads. The read before a change stops starting new retry waits at the midpoint of the status operation budget. A read already in flight at the midpoint still runs to the end of the budget, which its signal spans. A read refused until the midpoint fails with no set dispatched.

8. **Inside a batch item, request retry is off until the item dispatches its credential request.** The batch job runs each item's issuance inside `runWithoutRequestRetry`, an `AsyncLocalStorage` scope of its own, and resumes request retry from the dispatch hook (ADR-060). The scope holds one state object for each item, so a nested request context neither ends the suppression early nor restores it after dispatch, the next item starts suppressed, and work outside the item is unaffected. A request started before dispatch makes one attempt, also if it is still in flight when the item dispatches, because the client reads the scope once when a call starts. A repeatable read before dispatch keeps its per-attempt limit, where it has one; only the resends are off. The item ladder of ADR-060 retries the faults before dispatch. From dispatch on, nothing issues the item again, so the issue request, the document store and the identity resolver publish follow decisions 2 and 3: a `429` is resent within the call's deadline, and a `503` or a timeout is not.

9. **Each adapter logs retries through its own logger.** A warning names the origin and path, method, attempt, cause, and the wait or the reason retrying stopped, never headers, bodies or query strings. The two status-list calls make one attempt and emit no retry or give-up event.

## Consequences

A dependency that refuses a request for a few seconds no longer fails a status read, a verification, a stored-copy read or an operator backfill row. Operators see each retry in the logs.

A gateway that answers `429` for a request it did forward can now cause a repeated effect for an effectful call. The cases are listed on the operations page, and the assumption is stated there before any description of behaviour.

Inside a batch item, a `429` on the VCKit issue request that the retries get through settles the item `ISSUED`. One still refused after the retries is recorded as `OUTCOME_UNKNOWN`, although under decision 2 nothing was issued. While a dependency is refusing, the issue request, the store and the publish can each add up to about 30 seconds to an item.

Storing a credential and registering its links run without a caller deadline after signing, so a refusing gateway can add up to 30 seconds to each on the single issuance route.

A new adapter call must choose its marking. Leaving it unmarked is the default that never resends after a `503` or a timeout.

## Alternatives Considered

- **Retry in each adapter.** Rejected because every adapter would repeat the same timing, `Retry-After` parsing and cancellation rules, and a missed one would silently differ.
- **Derive "safe to repeat" from the HTTP method.** Rejected because VCKit's reads are `POST` requests and would never be retried.
- **Retry `503` for every call.** Rejected because an issue, store or registration may have taken effect before the `503` was returned.
- **Suppress request retry for the whole batch item.** Rejected because the item ladder retries only the faults before dispatch. A `429` on the store or the publish would then be final, leaving the credential unstored or not discoverable, and a refused issue request would settle the item `OUTCOME_UNKNOWN` although nothing was issued. Documenting that behaviour instead of changing it was also considered and not taken.
- **Carry the batch opt-out on the request context.** Rejected because `runWithRequestContext` replaces the store, so a nested context inside an item would switch retry back on.
- **Retry status mints and sets within the lock deadline.** Rejected because a wait holds the status list's lock and stalls every other change to that list.
- **Read only the IMF-fixdate form of `Retry-After`.** Rejected because RFC 9110 section 5.6.7 requires a recipient to accept the two obsolete forms, and refusing them would end a retry the server asked for.
- **A retry library or a dispatcher-level retry.** Not used. No retry library is a dependency of any workspace package, and `undici`, which offers a retrying dispatcher, is a dependency of `untp-utils` only. Undici's retry handler accepts retry options per request, so it could tell VCKit's `POST` reads from issuance. It does not provide this project's contract, which would have to be built around it: the caller's signal ending a wait and returning the held response, the caller's deadline bounding waits and dispatch, a `Retry-After` longer than 30 seconds returning the response rather than being shortened to the cap as undici 6.25 does, `Retry-After` dates read in the three RFC 9110 forms only rather than through `new Date`, the retry scope of a batch item, and a returned response that reads as one attempt's would. Using it would also make the services package depend on `undici` directly and route every adapter request through a dispatcher of its own.
- **Retry connection failures and `502` or `504` on reads.** Not taken, because the request was limited to `429`, `503` and timeouts. Revisit with evidence from deployments.
